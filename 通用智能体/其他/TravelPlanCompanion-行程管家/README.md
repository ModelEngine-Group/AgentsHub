# 行程管家 · 旅游规划助手（TravelPlan Companion）

基于 **Nexent v2.8.3** 构建的中文旅游规划智能体。它不写"攻略文"，而是产出一份**可以直接照着执行的行程单**：时间可落地、交通可衔接、预算能对账。

输入出发地、目的地、天数、人数、预算和偏好，即可得到逐日时间轴行程、住宿与美食建议、**可对账的预算表**、待核实清单和行前提醒；涉及实时票价、开放时间与天气时，会调用 `deepseek_search` 检索并标注来源与查询日期。

> 本目录中的 `agent.json` 由 Nexent 平台导出后脱敏，`deepseek_api_key` 已置空，不包含原开发者的租户标识或密钥。导入后需自行配置模型与搜索工具 Key。

## 功能

- **需求一次性问齐**：从输入中提取出发地、目的地、日期/天数、人数、预算、偏好与特殊需求；关键信息缺失时用一条消息集中追问，不做挤牙膏式反复提问。
- **可执行行程编排**：按上午/下午/晚上输出时间轴，每个条目含停留时长、点对点交通方式与耗时、参考费用；就近聚类减少折返，首尾日扣除抵达/返程时间。
- **节奏控制**：每天高强度景点不超过 2 个，午后转低强度；带老人或儿童时自动放缓。
- **预算闭环**：按往返交通、市内交通、住宿、餐饮、门票、备用金六科目估算，合计必须等于各项之和，并与行程条目金额一致；人数与晚数参与计算。
- **超支三档降本**：合计超预算时不砍质量凑数，而是给出「A 住宿降档 / B 交通替代 / C 门票取舍」三档方案，每档注明可省金额与新的合计。
- **事实与推测分离**：实时信息走 `deepseek_search` 并标注来源与查询日期；检索无果或结果冲突时写"待核实"并给官方核实渠道，禁止编造数字。
- **多轮增量修订**：用户改预算、改天数时，只输出变更部分并重新对账，不整篇重抄。

## 导入与配置

1. 在目标环境部署或登录 Nexent，获得智能体开发权限。
2. **模型**：进入模型配置页，添加模型（URL 如 `https://api.deepseek.com`，模型名 `deepseek-chat`）并验证连通性。
3. **导入智能体**：进入智能体开发 → 导入，选择本目录的 `agent.json`；按提示把 `model_ids` 映射到步骤 2 中配置的模型。
4. **配置工具密钥**：打开导入后的智能体 → 工具管理 → `deepseek_search` → 配置，填入你自己申请的 DeepSeek API Key（导出文件中的 `deepseek_api_key` 为空，不填则无法联网检索）。
5. **测试**：执行下方用例 1 与用例 2，确认模型应答与工具调用均正常后发布。

> 文件说明：`agent.json` 由 Nexent 平台导出后做了三处处理——清空 `deepseek_api_key`、清空 `tenant_id` 与作者信息、移除工具参数中的 `language`。最后一项是必要的：`language` 属于运行时参数，平台导出时会写入 `params`，但导入时会报 `Parameter language ... cannot be found`，导致「导出的文件无法再导入」。如你在自己的环境重新导出，请一并删除该项。

> 安全提醒：不要把 API Key、租户密码、会话令牌提交到仓库。若重新导出已配置的智能体，请再次检查工具参数中的密钥是否已清空。

## 使用示例与实测结果

以下四组用例在 Nexent v2.8.3 + DeepSeek 模型上实际运行，结果为真实输出摘要。

**用例 1：行程 + 预算（不依赖工具）**

输入：`两个人从重庆出发去成都玩两天一晚，总预算1500元，喜欢美食和熊猫。请直接给行程和预算表。`

实测：输出「假设说明 → Day1/Day2 时间轴表 → 住宿与美食 → 预算明细表 → 降本方案 → 待核实清单」。预算表给出「小计 1544 元 + 备用金 66 元 = 合计 1610 元」，并主动写明 **Day1 916 + Day2 628 = 1544 = 预算表小计**，与预算 1500 元对比后判定超支 110 元，给出 A 住宿降档 / B 交通替代 / C 门票取舍 及 A+B 组合（1480 元）四选一方案。

**用例 2：实时信息与来源标注**

输入：`查一下成都大熊猫繁育研究基地现在的开放时间和门票价格，注明来源。`

实测：触发 `deepseek_search`（执行记录可见工具调用），输出淡旺季分时段入园表、票价表与购票规则，逐条标注来源编号与「2026-11-02 查询」；对第三方平台与官方口径不一致之处主动指出差异；末尾附「待核实清单」并给出官方渠道。

**用例 3：一次性问齐需求**

输入：只给「我想去成都玩」（缺天数、人数、预算）。

预期：用一条消息集中追问关键项，不逐条挤牙膏；已给出的目的地不回问。

**用例 4：多轮增量修订**

在同一会话中继续输入：`预算改成1200元，其他条件不变，帮我重新规划并说明变化`

预期：保留出发地、目的地、人数和天数，只输出被改动的部分与新预算合计，并说明与上一版的差异。

> 说明：用例 1 与用例 2 为实测结果；用例 3、4 属于交互行为约定，建议导入后按上述输入回归一次。

## 设计取舍

- **不做"景点百科"**：景点介绍只保留与决策相关的信息（是否值得去、要多久、要不要预约），避免把行程单写成散文。
- **宁标"待核实"也不猜**：实时价格与开放时间的变化频率高，编造一个数字的代价远高于让用户多点一次官方链接。
- **把预算当成约束而不是总结**：很多行程助手在最后"估个总数"，本智能体要求三处金额（行程条目、明细、合计）互相咬合。

## 局限与说明

- 未接入地图路径规划、实时交通票务与气象专用 API；交通耗时与班次为经验性估算，不保证实时准确。
- 搜索结果可能包含过期或被转载失真的第三方资料，出行前请核对景区与交通运营方的官方渠道。
- 不执行购票、酒店预订、支付等真实交易。
- 联网检索依赖可用的 DeepSeek 服务额度，可能产生 API 成本。
