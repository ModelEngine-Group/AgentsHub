# 【通用】旅游规划助手（travel_planning_assistant）

## 简介

一个面向自由行的行程规划智能体。用户给出出发地、目的地、天数、预算之后，它输出可直接执行的逐日行程、分项预算明细和行前准备清单。门票价格、开放时间、预约政策通过 `tavily_search` 联网核实并标注来源；天气、交通班次、实时路况不在服务范围内，明确引导用户查询官方渠道，不编造实时数据。

基于 Nexent v2.7.0 开发。

> **与仓库内已有 `TravelPlanner-Agent` 的区别**：那个版本走 `deepseek_search`，定位是"什么都能搜"。本版本反过来做减法——**只搜三类会直接影响行程可行性和花费的信息，其余一律引导用户自查**，并且在预算上要求逐项列算式，让每一笔钱都能被人工核验。两者的取舍不同，可以共存。

> **脱敏声明**：`agent.json` 来自 Nexent 平台导出并已脱敏，不含租户 UUID、邮箱、API Key。`model_ids` 是导出机器的本地数据库 ID，**导入后必须重新选择模型**；`tavily_search` 的 `tavily_api_key` 已置空，**导入后必须填写自己的 Key**，否则联网核实功能不可用。

## 功能

- **逐日行程编排**：按天给出景点、时段、通勤方式和停留时长；单日景点不超过 4 个，同行人有老人或儿童时降到 3 个并标注休息点。
- **预算可核验**：每一项先写算式（如 `154 × 2人 × 2程 = 616元`）再相加，最后算余额，禁止只给合计数。算式错在哪一眼能看出来。
- **关键信息联网核实**：门票价格、开放时间、预约政策必须调 `tavily_search`，回答里带来源站点和日期，可用引用标记回溯。
- **能力边界管理**：天气、班次、实时路况不搜、不编数字，直接引导用户查 12306 或气象服务。
- **信息不足时追问**：出发地、目的地、天数、预算四项任一缺失就先问，不自行假设后硬给行程。
- **搜索次数受控**：同一问题最多搜 2 次，换取措辞只允许 1 次，避免多个来源的价格混在一张表里。

## 运行环境与依赖

| 项目 | 配置 |
| --- | --- |
| 平台版本 | Nexent v2.7.0 |
| 智能体变量名 | `travel_planning_assistant` |
| 显示名 | 旅游规划助手 |
| 大语言模型 | 任意支持 function calling 的对话模型（开发与验收使用 `deepseek-v4-flash-0731`） |
| 内置工具 | `tavily_search`（唯一外部依赖） |
| 知识库 / Skill / MCP | 均未使用 |
| `max_steps` | 15 |

关于模型：开发过程中对比测试过多个模型，`deepseek-v4-flash-0731` 的 tool call 稳定，能在单轮内正确判断"该搜"与"不该搜"。换用其他模型时建议先跑下面的验收用例，重点是第 2、3、4 条——**换模型后最容易退化的不是回答质量，而是"忍住不搜"的判断力**。

关于输出配额：本智能体在推理型模型上运行过，思考过程会占用输出 token。**导入后请确认所用模型的"输出预留 Token 数"不低于 8192，建议 16384**，否则长行程可能只输出思考不输出正文。

## 导入与配置

1. 在 Nexent 中导入 `agent.json`。
2. 打开智能体配置 →「模型与提示词」，**重新选择模型**（导出文件里的 `model_ids` 是原机器的本地 ID，在你的环境里不存在或指向别的模型）。
3. 打开「工具」→ `tavily_search` → 填入自己的 `tavily_api_key`。Key 可在 [tavily.com](https://tavily.com) 免费申请，免费额度每月 1000 次，超额后请求停止、不会自动扣费。
4. 检查模型容量配置，确认「输出预留 Token 数」≥ 8192。
5. 在调试窗口按「使用示例」逐条验证，重点看第 2、3、4 条是否真的没有触发搜索。

**安全提醒**：不要把 API Key、租户密码、登录令牌提交到仓库。本仓库中的 `agent.json` 已清空 `tavily_api_key`。

## 使用示例与预期输出

### 示例 1：需要联网核实的信息

输入：

```
成都欢乐谷门票多少钱
```

预期：调用 `tavily_search`，返回分档票价并标注来源（官网 / OTA 平台），带可点击的引用标记。开发环境实测结果是官网成人团 ¥207、中小学生团 ¥140，OTA 平台"¥150 起"——两者口径不同，回答里会分开标注。

### 示例 2：信息严重不足

输入：

```
帮我规划旅游
```

预期：**不编行程**，追问三项：出发地和目的地、天数和出发时间、预算和同行人数。问完说明下一步会做什么。

### 示例 3：超出服务范围

输入：

```
成都国庆期间天气怎么样
```

预期：**不调用搜索**，说明天气不在服务范围，建议查看天气 App 或中国天气网，可补充季节特点但不给具体温度数字。

### 示例 4：完整规划

输入：

```
我想国庆去成都玩4天，从重庆出发，两个人，预算5000，喜欢美食和古镇
```

预期输出结构：

1. 需求确认（复述关键约束）
2. 逐日行程表（日期 / 时段 / 景点 / 通勤 / 停留时长）
3. 预算明细（交通、住宿、门票、餐饮分项算式 + 合计 + 余额）
4. 行前准备清单
5. 需自行核实的事项（天气、班次）

## 设计说明

**为什么预算不用代码执行器算。** 旅行预算是纯加减乘除，要求"每项先写算式再相加"，错误是肉眼可核验的。相比之下，让模型调代码执行器算出一个总数，中间过程不可见，出错反而更难发现。代价是模型偶尔会在算术上出错，但有算式就能一眼定位。

**为什么限定搜索次数。** 早期版本出现过同一景点连搜 3 次（`门票价格 2026 官方` → `门票价格 2026年 最新` → `加上 票价 多少钱`）的情况。多搜不会更准，反而会把不同来源的价格拼进同一张表，最终无法回答"这个数字哪来的"。限制 2 次之后，回答要么有明确来源，要么老实标"未核实"。

**为什么主动放弃天气和班次。** 这两类信息的正确来源是气象服务和 12306，任何搜索工具拿到的都是二手数据。助手给一个"10 月 3 日成都多云 22 度"，用户信了就是误导。明确说"请自行查询"是更专业的表现。

## 已知限制

- 中文景点搜索精度依赖 Tavily 的索引质量，小众景点可能返回空结果，此时会标注"未核实"。
- 未配置 rerank 模型和知识库，检索质量仅依赖 Tavily 返回的排序。
- 交通费用只给参考价（如重庆到成都高铁二等座约 150 元），实际票价和班次以 12306 为准。
