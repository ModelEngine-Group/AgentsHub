# 评论风格指南

> 目标：让作者**愿意改、知道怎么改**。一条好评论 = 位置 + 证据 + 影响 + 动作。

## 基本原则

1. **对事不对人**：说「这段查询把 uid 拼进了 SQL」，不说「你根本不懂安全」。
2. **一条一个点**：不要把 5 个问题塞进一条评论。
3. **给证据**：引用具体代码或输入，不写「这里可能有问题」。
4. **给动作**：修复建议要能直接照做。
5. **分级**：P0/P1 明确说「阻塞」；P2 说「建议」；P3 可以不说。
6. **不教育**：不展开教科书，不贴大段文档链接。

## 好/坏对照

### 1. SQL 注入

差：`这里 SQL 注入很危险，建议改一下。`
好：
> **P1 安全**：`uid` 来自 query 参数并拼进 SQL，构造 `1 OR 1=1` 可绕过条件。
> 建议：`cur.execute("... WHERE id=%s", (uid,))`。

### 2. 空值

差：`注意空指针。`
好：
> **P1 正确性**：`items[0]` 在空列表时抛 `IndexError`；上游 `parse()` 可能返回 `[]`。
> 建议：先判空并返回明确错误，或改用 `next(iter(items), None)`。

### 3. 可变默认参数

差：`默认参数不要用可变对象。`
好：
> **P2 正确性**：`store={}` 在函数定义时创建，多次调用共享同一 dict，第二次请求会读到第一次的数据。
> 建议：`store=None`，函数体内初始化。

### 4. 裸 except

差：`except 太宽了。`
好：
> **P2 健壮性**：裸 `except` 会吞掉 `KeyboardInterrupt`，且失败后返回 `False` 无法定位原因。
> 建议：捕获 `FileNotFoundError`，其他异常记录日志后抛出。

### 5. 性能

差：`这里有性能问题。`
好：
> **P1 性能**：循环内对每个 `user_id` 查一次库，100 条数据会产生 101 次查询。
> 建议：先 `IN` 批量查一次，再在内存里组装。

### 6. 测试

差：`建议补充测试。`
好：
> **P2 测试**：新增了 `if not items: raise` 分支，但没有空列表用例。
> 建议：补 `test_mean_empty_raises`。

### 7. 命名

差：`变量名不规范。`
好（仅当影响理解时）：
> **P3 可读性**：`d` 同时表示 deadline 和 duration，容易误用。
> 建议：拆成 `deadline` / `duration_sec`。

### 8. 无问题

差：`看起来没问题。`
好：
> 本次审查覆盖 3 个文件、86 行新增；未发现 P0/P1 问题。有 1 处 P2（缺超时）已在上方说明。

## 中文措辞替换表

| 不要写 | 改成 |
|---|---|
| 这里有问题 | 具体说明什么输入导致什么后果 |
| 建议优化 | 给出具体改法或目标 |
| 注意安全 | 指出攻击面与利用方式 |
| 最好加个判断 | 指出哪个值可能为空、空时应该怎样 |
| 不太规范 | 引用团队规范条目或说明可读性影响 |

## 长度

- 单条评论 ≤ 5 行；超过说明没提炼清楚。
- 总结 ≤ 3 行：结论 + 数量 + 是否阻塞。
